# 주식 자동매매 및 예측 시스템 UX/UI 종합 검토 보고서
**Consolidated UX/UI Review Report for the Stock Trading System**

---

## 1. 서론 및 요약 (Executive Summary)

본 보고서는 통합 주식 자동매매 및 예측 시스템(Consolidated Stock Trading & Prediction System)의 사용자 경험(UX, User Experience) 및 사용자 인터페이스(UI, User Interface) 품질을 전반적으로 개선하기 위해 작성된 수석 UX 디자이너 관점의 전문 검토서입니다. 

본 시스템은 XGBoost 회귀(Regression), Surge 분류기(Classifier), Lead-Lag 상관관계 분석, VCP(Volatility Contraction Pattern) 규칙 및 머신러닝(ML) 등 5대 예측 전략을 기반으로 한국(KOSPI, KOSDAQ, KONEX) 및 미국(S&P 500) 시장의 3,379개 종목을 매일 자동으로 분석하는 강력한 성능을 자랑합니다. 그러나 시스템의 백엔드 아키텍처(Backend Architecture)가 고도화된 것에 비해, 운용자(Operator)와 트레이더(Trader)가 직면하는 인터페이스와 산출물은 정보 아키텍처(Information Architecture)와 가시성(Visibility) 측면에서 심각한 인지적 과부하(Cognitive Overload)를 유발하고 있습니다.

따라서 본 보고서는 ① 5개 출력 파일, ② 텔레그램 알림, ③ GitHub Actions 워크플로우, ④ 웹 대시보드 UI, ⑤ CLI 실행 경험의 5대 핵심 도메인을 정밀 진단하고, Jakob Nielsen의 10대 사용성 휴리스틱(10 Usability Heuristics)을 기반으로 시스템을 평가합니다. 최종적으로 단기(P0/P1) 및 중장기(P2/P3) 실행 로드맵을 제시함으로써, 개발자 중심의 스크립트 모음에서 시장 환경 변화에 기민하게 대응할 수 있는 엔터프라이즈급 금융 솔루션으로의 UX 전환을 도모하고자 합니다.

## 2. 5대 UX 영역의 전문 검토 (Professional Review of 5 UX Domains)

### Domain 1: 5대 출력 파일 (5 Output Files)

매일 파이프라인 연동 결과물로 생성되는 텍스트 기반 출력 파일은 정보의 시각적 위계(Visual Hierarchy)가 파편화되어 있어 정보 발견 가능성(Discoverability)을 현저히 저해하고 있습니다.

#### [발견된 문제점 (UX Pain Points)]
1. **압도적인 텍스트 용량 및 스크롤 피로도 (Information Overload)**
   `pipeline_result.txt` 파일은 대략 1MB 크기에 달하며 무려 25,341줄의 텍스트 데이터가 나열됩니다. 파일 헤더의 8개 Horizon(1d ~ 200d) 정보가 단순 텍스트로 중첩되어 있어 운용자가 텍스트 뷰어로 의미 있는 종목을 걸러내기 불가능합니다. (근거 자료: `trading_system/pipeline_result.txt` 8~10행의 `--- KOSPI (all 917 symbols) ---` 포맷)
2. **지표 및 단위 레이블의 모호성 (Conceptual Ambiguity)**
   `lead_lag_predictions.txt` 파일 내에서 특정 종목의 상관도가 `103.52%`처럼 100%를 초과하는 수치로 기재되어 있습니다. 이 수치가 단순 피어슨 상관계수(Pearson Correlation Coefficient)인지, 예측 수익률인지, 혹은 자체 스케일링 가중치인지 명확한 단위나 주석이 기여되어 있지 않아 의사결정에 혼란을 유도합니다. (근거 자료: `trading_system/lead_lag_predictions.txt` 53행의 `1. [SP500] CPRT (Copart): 103.52%`)
3. **데이터 노이즈 및 아웃라이어 미필터링 (Unfiltered Data Outliers)**
   수집 과정의 오류나 주식 분할 정보의 미반영으로 인해 `+890.72%`와 같은 현실 불가능한 변동률을 가진 아웃라이어가 'Top Return Leaders' 목록에 그대로 노출되어 보고서의 전체 신뢰성을 훼손합니다. (근거 자료: `trading_system/lead_lag_predictions.txt` 75행의 `1. 293940 (신한알파리츠): +890.72%`)

#### [실행 가능한 개선 방안 (Actionable Solutions)]
- **CSV/JSON 포맷 분리 및 텍스트 요약화**: 25,000줄 이상의 로우 데이터(Raw Data)는 사람이 직접 열지 않도록 `pipeline_result.csv`로 내보내고, `pipeline_result.txt` 파일에는 각 시장/Horizon별 상위 10개 핵심 요약 카드(Card)만 배치하여 가독성을 개선합니다.
- **메트릭 명칭의 표준화 및 용어 사전(Glossary) 제공**: 파일 헤더 영역에 산출식의 메트릭 이름(예: `Lag-1 Lead-Lag Correlation Index`)을 명시하여 직관적인 이해를 돕습니다.
- **이상치 탐지 알고리즘(Anomaly Detection) 기반 차단**: 하루 변동률이 극단적(예: ±30% 초과)이거나 상한가/하한가 제한폭을 벗어난 종목에 대해서는 자동 경고 라벨을 부착하거나, 순위 목록에서 자동 제외하는 데이터 정제 레이어를 구축합니다.

### Domain 2: 텔레그램 알림 (Telegram Notifications)

`bot_engine.py`와 `telegram_bot_runner.py`를 통해 제공되는 알림 서비스는 단순한 정보 전송용 채널로만 활용되고 있어, 긴급 상황에서의 즉각적인 반응성(Responsiveness)이 떨어집니다.

#### [발견된 문제점 (UX Pain Points)]
1. **알림 구조의 평면성 및 긴급도 계층 결여 (Flat Notification Hierarchy)**
   매수/매도 주문 접수(placed) 알림, 단순 봇 시동(start) 메시지, 그리고 매우 심각한 손절매(stop_loss)나 위기 감지(crisis_detected) 상황이 동일한 텍스트 폰트 두께와 유사한 이모지 레이아웃으로 발송되어 시각적으로 위급함을 인지하기 어렵습니다. (근거 자료: `trading_system/src/telegram_bot/bot_engine.py` 718~732행의 알림 분기문)
2. **단방향 통보에 따른 액션 유도 부재 (Lack of Actionable Callbacks)**
   주문이 거부되었거나 손절매가 터졌을 때 사용자가 텔레그램 내에서 즉각 대응할 수 있는 인터랙션 도구(인라인 버튼 등)가 존재하지 않습니다. 결국 사용자는 PC를 켜고 터미널을 열어 대응해야 하므로 조작 지연(Latency)이 발생합니다.
3. **배치 작업 완료 알림 내 핵심 지표 누락 (Poor Batch Run Summary)**
   `/predict` 명령어 실행 시 백그라운드 파이프라인이 돌지만 완료 후 발송되는 보고서가 지나치게 단조롭습니다. 훈련 소요 시간, 수집 성공율, 무시된 거래 정지 종목 수 등 운용 상의 필수 메트릭이 누락되어 있습니다. (근거 자료: `trading_system/src/telegram_bot/bot_engine.py` 749~755행의 일일 보고서 생성 구조)

#### [실행 가능한 개선 방안 (Actionable Solutions)]
- **시각적 위험도 등급(Severity Levels) 정의**: 알림 메시지의 중요도를 `INFO`, `WARNING`, `CRITICAL`로 세분화하고, 테두리 블록(HTML formatting)과 컬러 이모지를 적용해 중요 신호를 즉각 구분할 수 있도록 합니다.
- **인라인 키보드(Inline Keyboard Button)를 통한 제어 연동**: 매수/매도 체결 알림 하단에 `[주문 취소]`, `[대시보드 보기]`, `[리스크 보고서]` 등 API 콜백 버튼을 제공하여 원클릭 대응을 가능하게 합니다.
- **구조화된 완료 요약 템플릿 도입**: 파이프라인 구동 완료 알림에 '학습 수행 여부', '데이터 갱신 종목 수', '동작 시간' 등을 테이블 형태로 가시화해 요약 제공합니다.

### Domain 3: GitHub Actions 운영 경험 (GitHub Actions Operator Experience)

GHA(GitHub Actions)는 예약 크론(Cron)을 통해 매일 파이프라인을 자동 구동하지만, 개발자 콘솔의 로우 로그(Raw Log)에 의존하고 있어 에러 진단성(Diagnostics)이 떨어집니다.

#### [발견된 문제점 (UX Pain Points)]
1. **장시간 빌드 시 진행 상태 모니터링의 모호성 (Macro Timeout & Lack of Feedback)**
   `timeout-minutes: 180`으로 워크플로우에 긴 제한 시간이 걸려 있지만, CLI 내부에서 각 시장별 학습 진행 상태를 시각화해 주지 않아 현재 수집 단계인지, 학습 단계인지, 추론 단계인지 전체 진행 흐름을 가늠하기 어렵습니다. (근거 자료: `.github/workflows/pipeline.yml` 20~21행의 matrix 및 timeout 설정)
2. **에러 발생 시 디버깅의 고통 (Debug Difficulty)**
   XGBoost 회귀 모델 학습 또는 API 속도 제한 오류로 인해 파이프라인 실행 중(Cite: `run_pipeline.py` 1269~1271행의 메인 실행부) 예외가 터지면, 운용자는 수천 줄의 콘솔 로그를 일일이 아래로 내리며 스택 트레이스(Stack Trace)를 뒤져야 원인을 찾을 수 있습니다.
3. **아티팩트 및 릴리즈 뷰어의 불친절함 (Manual Asset Inspection)**
   매일 빌드된 `.txt` 파일들이 릴리즈 자산으로 업로드되지만(Cite: `.github/workflows/pipeline.yml` 208행), 릴리즈 화면에서 예측 결과의 종합적 헬스 체크(Health Check) 지표나 비교 테이블을 바로 확인하지 못하고 파일을 매번 다운로드해서 확인해야 합니다.

#### [실행 가능한 개선 방안 (Actionable Solutions)]
- **GitHub Step Summary 기능 내 요약 테이블 출력**: 워크플로우 실행 시 `$GITHUB_STEP_SUMMARY`에 분석 통계(예: 수집 완료된 종목 수, 모델 저장 여부)를 마크다운 포맷으로 자동 작성해 Actions 메인 화면에서 한눈에 결과를 보게 합니다.
- **Slack/Telegram 에러 웹훅 연동**: 빌드 실패 단계가 발견되면, 즉각 실패 원인 메시지와 실패한 깃허브 액션 실행 URL(Run URL)을 에러 로그의 마지막 10줄 요약과 함께 텔레그램으로 즉시 발송합니다.
- **머신 리더블 메타데이터(JSON) 자동 릴리즈**: 텍스트 파일 외에도 통계 수치가 기록된 `summary.json`을 패키징해 함께 릴리즈함으로써 외부 BI 툴이나 스크립트가 파싱하기 쉽게 만듭니다.

### Domain 4: 웹 대시보드 UI/UX (Web Dashboard UI/UX)

`dashboard.py` 기반의 Plotly Dash 웹UI는 복잡한 데이터 분석 기능을 제공하나, 계층적 정보 아키텍처(Information Architecture)와 일관성이 배제되어 있어 직관성이 저하됩니다.

#### [발견된 문제점 (UX Pain Points)]
1. **홈/종합 화면(Landing Overview)의 누락**
   대시보드 진입 시 시스템 전체 상태를 요약하는 대시보드 홈(Home) 화면이 없습니다. 사용자는 진입하자마자 세부 그래프 탭을 선택하고 조회 대상을 드롭다운으로 고르는 복잡한 인터랙션을 수행해야만 데이터를 볼 수 있습니다. (근거 자료: `trading_system/src/web/dashboard.py` 28~34행의 레이아웃 정의)
2. **오랜 백그라운드 연산 시 로딩 인디케이터 부재 (Lack of Loading State Feedback)**
   "Run Prediction Pipeline" 또는 "Run Post-Market Scoring" 버튼을 클릭하면 서버 단에서 매우 긴 데이터베이스 트랜잭션 및 추론 연산이 수행되지만, 화면에 스피너(Spinner)나 처리 중(Loading) 표시가 나타나지 않아 시스템이 멈춘 것처럼 보입니다. (근거 자료: `trading_system/src/web/dashboard.py` 195~205행)
3. **모바일 해상도 미지원에 따른 레이아웃 파손 (Fixed Grid Layout)**
   차트와 테이블이 데스크톱 가로형 그리드로 고정되어 있어 태블릿이나 스마트폰 화면으로 대시보드에 접속 시 UI가 겹쳐 보이거나 가로 스크롤이 끝없이 발생해 현장 모니터링이 불가능합니다.

#### [실행 가능한 개선 방안 (Actionable Solutions)]
- **메인 종합 상황판(Dashboard Overview) 신설**: 최상단에 계좌 잔고, 시장 Regime 상태, 최근 파이프라인 구동 시각, 경보 발생 횟수 등을 표시하는 요약 카드 4종을 영구 배치합니다.
- **Dash `dcc.Loading` 컴포넌트 전면 적용**: 데이터를 불러오거나 파이프라인 연동 버튼을 활성화할 때 전체 화면을 차단하는 로딩 오버레이(Loading Overlay) 혹은 스피너를 노출하여 더블 클릭을 방지하고 작업 진행 중임을 인지시킵니다.
- **CSS Flexbox/Grid와 미디어 쿼리를 반영한 반응형 UI 구현**: 화면 크기가 768px 미만으로 좁아질 때 가로 배열 차트를 세로로 정렬하고 테이블 폰트 크기를 유동적으로 스케일링하는 반응형 웹 디자인을 도입합니다.

### Domain 5: 중앙 CLI 실행 경험 (Central CLI Execution Experience)

`run_pipeline.py`를 단독 실행하거나 디버깅할 때 발생하는 콘솔 출력 정보는 터미널 화면을 불필요한 정보로 도배하여 모니터링의 효율성을 가로막습니다.

#### [발견된 문제점 (UX Pain Points)]
1. **스트리밍 로그 폭탄으로 인한 진행도 인지 불가 (Text Flooding)**
   3,379개 종목을 수집하고 피처 엔지니어링을 처리하는 동안 단순 텍스트 줄바꿈 로그가 빠르게 올라갑니다. 현재 몇 퍼센트(%) 완료되었는지, 혹은 남은 시간이 얼마인지 진행률 표시줄(Progress Bar)이 전혀 없어 실행 중 터미널을 마냥 바라봐야 하는 불편함이 있습니다. (근거 자료: `trading_system/run_pipeline.py` 1230~1248행의 검증부 로그 출력)
2. **명령 명령행 인자(CLI Arguments) 옵션 결여**
   실행 옵션들이 환경 변수나 `.env` 파일에 하드코딩되어 동작합니다. 특정 대상 시장만 즉시 추론하거나 학습을 건너뛰고 싶을 때 매번 쉘의 `export` 명령어나 설정 파일을 편집해야 해 조작 유연성(Flexibility)이 떨어집니다.
3. **에러 발생 시 비정상 종료와 불친절한 가이드 (Unfriendly Error Trace)**
   yfinance 통신 오류나 SQLite DB 락이 발생할 때 프로그램이 에러 스택 트레이스만 뱉으며 그대로 뻗어버립니다. 일반 사용자나 트레이더가 이 터미널 에러를 보았을 때 어떻게 시스템을 재복구해야 하는지에 대한 가이드 라인(Actionable Guide)이 전무합니다.

#### [실행 가능한 개선 방안 (Actionable Solutions)]
- **`rich.progress` 또는 `tqdm` 라이브러리를 활용한 TUI(Terminal User Interface) 적용**: 스크롤 로그 대신 고정 영역에 실시간 이모지와 컬러 진행 표시바(Visual Progress Bar)를 노출해 터미널 시인성을 극대화합니다.
- **`argparse` 라이브러리를 활용한 정교한 CLI 인수 체계 구축**: `python run_pipeline.py --target KOSPI --skip-training --debug` 형태로 명령어 수준에서 즉각적인 제어가 가능하게 만듭니다.
- **에러 핸들러 래핑 및 문제 해결 플레이북(Playbook) 출력**: 치명적인 에러 캐치 시, 박스 형태의 터미널 UI 안에 경고 문구와 함께 "조치 가이드: SQLite 파일 쓰기 권한을 확인하거나, 인터넷 연결을 점검하십시오."를 인쇄하여 자가 복구성을 부여합니다.

## 7. 상세 파일 인용 및 기술적 근거 (Direct File Citations)

본 보고서에 기술된 UX 문제와 제안은 시스템의 실제 코드베이스 및 결과 파일 구조에 기반하고 있습니다. 주요 근거가 되는 코드라인 인용은 다음과 같습니다.

1. **지나친 스크롤 스크롤 압박과 대용량 텍스트 출력의 근거**
   `trading_system/pipeline_result.txt` 파일의 시작부에서는 다음과 같이 25,000줄 이상의 출력을 단순 나열형으로 시작합니다:
   > *인용 라인 8~10:*
   > ```
   > --- KOSPI (all 917 symbols) ---
   >   1. 308170 (씨티알모빌리티): +0.54%
   >   2. 064400 (LG씨엔에스): +0.54%
   > ```
   이것은 8개 Horizon에 걸쳐 3,300여 종목을 매번 인쇄하므로 텍스트 가독성을 저해하는 주된 원인입니다.

2. **단위 혼란 및 필터링되지 않은 변동률 이상치 발견의 근거**
   `trading_system/lead_lag_predictions.txt` 파일에서는 % 단위의 왜곡 및 아웃라이어 정제 결여 현상이 뚜렷하게 관찰됩니다:
   > *인용 라인 53:*
   > ```
   >   1. [SP500] CPRT (Copart): 103.52%
   > ```
   > *인용 라인 75:*
   > ```
   >   1. 293940 (신한알파리츠): +890.72%
   > ```
   CPRT의 103.52%는 단순 상관관계 스코어 스케일링이 누락되었음을 시사하며, 신한알파리츠의 +890.72%는 주식 병합 등 외부 데이터의 급변 이벤트가 예외 필터링 없이 통계치에 흘러들어 간 증거입니다.

3. **VCP 패턴 결과 파일 내 시각적 소음 및 볼륨 경고 미흡의 근거**
   `trading_system/vcp_patterns.txt` 20~22행에서는 다음과 같은 출력이 반환됩니다:
   > *인용 라인 20~22:*
   > ```
   >   2. [SP500] HST (Host Hotels & Resorts)
   >        Score: 100/100 | Current range: 2.8% | Contraction: 2.8% > 2.9% > 3.0% > 3.7% > 3.8%
   >        Above MA50: ✓ | Above MA200: ✓ | Near high: ✓ | Volume declining: ✗
   > ```
   거래량 감소 조건이 충족되지 않았음에도(`Volume declining: ✗`) VCP Score가 동일하게 100/100으로 산출되어 수치적 일치성(Consistency)에 혼란을 주며, 이에 대한 시각적 보완이 요구됩니다.

4. **GitHub Actions 런타임 진행률 모니터링 누락의 근거**
   `.github/workflows/pipeline.yml` 워크플로우 명세서 내에서는 대기 타임아웃과 매트릭스 구동만이 선언되어 있고, 세부 파이프라인의 진행 통계를 GHA UI상에 갱신하는 훅이 배제되어 있습니다:
   > *인용 라인 20~21:*
   > ```yaml
   >         target: [SP500, KOSPI, KOSDAQ, KONEX]
   >     timeout-minutes: 180
   > ```
   3시간의 실행 타임아웃 동안 콘솔 로그를 들여다보지 않는 한 구체적 진행 상황을 파악할 수 없는 구조적 원인입니다.

5. **CLI 실행 명령 환경 변수 전도 및 입출력 제어 불가 근거**
   `trading_system/run_pipeline.py` 파일의 진입 스크립트는 실행 제어 매개변수를 콘솔 인자 대신 오직 `.env` 환경 변수에만 의존하여 시작합니다:
   > *인용 라인 1269~1271:*
   > ```python
   > if __name__ == "__main__":
   >     execute_prediction_pipeline()
   > ```
   이로 인해 운용자는 매번 파라미터를 바꾸기 위해 파일을 텍스트 에디터로 열어야 하는 조작 지연을 겪게 됩니다.

6. **대시보드 구동 방식의 투박함 및 로그 노출 근거**
   `trading_system/run_dashboard.py`에서는 대시보드 서버가 로컬 전용으로 단순 반복 실행되며, 실행 상태가 쉘에 무가공 인쇄됩니다:
   > *인용 라인 17~20:*

   이것은 터미널을 종료하면 웹 UX도 같이 꺼져 버리는 백그라운드 데몬화의 미흡과 UI 진입 전 안내의 미비점을 보여줍니다.

7. **웹 대시보드 탭 중심 레이아웃 및 종합 요약의 부재 근거**
   `trading_system/src/web/dashboard.py`의 UI 레이아웃 선언부를 보면, 전체 요약 화면이 배제되고 바로 세부 탭들로 시작되는 파편화된 화면 네비게이션을 확인할 수 있습니다:
   > *인용 라인 28~30:*

   >         html.H1("Trading System Dashboard"),
   > ```

## 8. 결론 (Conclusion)

통합 주식 자동매매 및 예측 시스템은 대규모 주식 우주(Universe)를 효과적으로 분석하는 매우 훌륭한 백엔드 엔진을 갖추고 있습니다. 그러나 본 검토를 통해 드러난 텍스트 폭탄, 단위 및 이상치로 인한 노이즈, 단방향 알림, 로딩 피드백 부재 등의 UX 마찰 지점들은 실제 트레이더와 시스템 운영진이 실전 매매에서 신속하고 정확한 의사결정을 내리는 데 큰 걸림돌이 됩니다.

본 보고서에서 제시한 P0 레벨의 핵심 개선안들—특히 **대시보드 로딩 표시 장착**, **콘솔 TUI 진행률 도입**, **텔레그램 알림 긴급도 차별화** 및 **GHA 에러 웹훅 연동**—은 상대적으로 적은 구현 리소스로 시스템의 운영성(Usability)과 복구 능력을 세계적 수준으로 격상시킬 수 있는 고효율 프로젝트입니다. 이들을 신속히 적용하여 개발자 중심의 스크립트 모음을 진정한 의미의 금융 거래 의사결정 지원 시스템(DSS, Decision Support System)으로 정제해 나갈 것을 강력히 권고합니다.
